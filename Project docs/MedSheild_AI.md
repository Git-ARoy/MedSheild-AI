# MedShield AI - Defensive Agent Architecture for HomeoCare

> Filename intentionally uses the requested spelling: `MedSheild_AI.md`. The product name inside the code and UI remains **MedShield AI**.

## 1. Purpose

This document replaces the original MedShield MVP architecture based on a frontend **"Simulate Attack"** button.

That simulation feature is no longer the core product and must be removed from the application.

MedShield AI must now operate as a **defensive cybersecurity agent protecting the HomeoCare AWS digital twin**. Attacks are generated by a controlled external adversary-emulation layer, with **Stratus Red Team** as the preferred initial integration for AWS techniques. MedShield must observe real security telemetry from the HomeoCare sandbox, investigate the activity against the hospital digital-twin graph, determine cyber and clinical impact, select an appropriate defensive response, execute a constrained response action, and verify whether the attack path has been interrupted.

The new product loop is:

```text
Real HomeoCare AWS Activity
          |
          v
 CloudTrail / CloudWatch
          |
          v
      EventBridge
          |
          v
   MedShield Intake
          |
          v
   Detection + Correlation
          |
          v
 Hospital Digital Twin
          |
          v
 Attack Path + Blast Radius
          |
          v
    Gemini Agent Reasoning
          |
      fallback:
   Local Gemma 4 12B
          |
          v
   Response Decision
          |
          v
 Constrained AWS Defense Tool
          |
          v
  Verify Containment
          |
          v
 Update HomeoCare Twin
```

This architecture is the product. There should be no fake attack log generator masquerading as the primary detection mechanism.

## 2. Core product thesis

MedShield is designed around one problem:

> **When a cyberattack enters a hospital environment, security teams need to know not only whether an asset is compromised, but what clinical services become reachable and which containment action minimizes both cyber risk and clinical disruption.**

The system must therefore combine:

- AWS security telemetry
- deterministic asset/dependency analysis
- AI-based investigation/reasoning
- constrained defensive actions
- post-action verification

Gemini is the intelligence layer, not the entire security system.

## 3. Remove the old simulation feature

### Delete or deprecate

Remove the existing frontend flow that starts an artificial attack sequence using an endpoint such as:

```text
POST /api/simulate
```

or any equivalent endpoint that manufactures events only for the purpose of triggering the UI.

Remove:

- `simulate attack` as the primary dashboard CTA;
- fake event streams presented as live security telemetry;
- frontend-only attack progression logic;
- hardcoded `demo_analysis()` results as the normal production path;
- UI wording implying that an attack actually occurred in AWS when only a local mock was executed.

The deterministic fallback may remain as a **last-resort demo availability mechanism**, but it must never masquerade as live AWS detection.

### Replace with

The primary action should be:

**Monitor HomeoCare**

and the incident workflow should be event-driven.

For a judge demonstration, include an explicit **Red Team Activity** indicator that links the incident to the controlled Stratus sandbox rather than inventing frontend events.

## 4. MedShield agent responsibilities

The agent is responsible for six major stages.

### Stage 1: Observe

Consume security events from AWS.

Minimum event sources:

- CloudTrail
- CloudWatch Logs where applicable
- EventBridge-routed security events

Each normalized event should contain enough context to identify:

- timestamp
- AWS account
- region
- event source
- event name
- actor identity
- source IP where available
- target resource
- target resource ARN where available
- request/result status
- raw event reference

AWS CloudTrail records API activity and includes identity/request context, while EventBridge can route CloudTrail events to targets such as Lambda. citeturn190631search1turn190631search2turn190631search4

### Stage 2: Detect and correlate

Do not send every isolated event blindly to Gemini.

The deterministic detection layer should first:

- normalize event fields;
- map AWS ARNs to HomeoCare asset IDs;
- identify unusual identity/resource relationships;
- group related events within a time window;
- detect privilege or access escalation indicators;
- determine whether an event touches a critical HomeoCare asset;
- construct a candidate attack sequence.

Example:

```text
09:41 IAM access anomaly
09:42 privileged API call
09:42 pharmacy API accessed
09:43 device gateway accessed
```

becomes:

```text
Candidate incident
identity_service
    -> pharmacy_api
    -> device_gateway
```

### Stage 3: Investigate

The agent must use explicit tools against the digital twin rather than inventing infrastructure facts.

Required investigation tools:

```text
get_asset(asset_id)
get_asset_by_arn(arn)
get_identity(identity_id)
get_permissions(identity_id)
get_dependencies(asset_id)
trace_attack_path(source_asset, target_asset)
get_clinical_impact(asset_id)
get_active_incidents()
get_recent_events(asset_id, window)
```

Example reasoning workflow:

```text
New CloudTrail event
    |
    v
Identify actor
    |
    v
Map actor to identity_service
    |
    v
Resolve target asset
    |
    v
Check allowed relationships
    |
    v
Trace reachable clinical assets
    |
    v
Calculate blast radius
```

### Stage 4: Reason and plan

Gemini should receive a compact, structured investigation context instead of an unbounded stream of raw logs.

The context should contain:

- normalized event sequence;
- affected assets;
- identity and privilege information;
- relevant dependency path;
- asset criticality;
- clinical metadata;
- candidate containment actions;
- operational impact of each action;
- known evidence and timestamps.

Gemini must return structured JSON matching the shared incident-analysis schema.

The model should answer:

1. What happened?
2. Is there a coherent attack pattern?
3. Which attack stage is currently active?
4. What assets can the actor reach?
5. What clinical services are potentially affected?
6. What response action should happen next?
7. Why is that response preferable to more disruptive alternatives?
8. What evidence supports the recommendation?

### Stage 5: Act

The agent must call only constrained, allow-listed defensive tools.

Required initial tools:

```text
revoke_identity_access(identity_id)
revoke_active_sessions(identity_id)
restrict_identity_to_role(identity_id, role_id)
block_source_ip(ip)
isolate_homeocare_asset(asset_id)
restore_homeocare_asset(asset_id)
```

Do not expose generic tools such as:

```text
execute_shell(command)
run_aws_cli(command)
execute_arbitrary_lambda(payload)
```

The agent must not be able to turn a natural-language instruction into arbitrary AWS administration.

Each defense tool must:

1. validate that the target belongs to the HomeoCare sandbox;
2. validate that the action is permitted for that asset class;
3. record the proposed action;
4. execute the bounded operation;
5. return a structured result;
6. emit an audit event.

### Stage 6: Verify

After a defensive action, MedShield must confirm whether the threat path changed.

Example:

```text
Before defense:
compromised_identity -> pharmacy_api -> device_gateway

Action:
revoke_identity_access(compromised_identity)

After defense:
compromised_identity -X-> pharmacy_api
```

The agent should perform a post-action query such as:

```text
get_permissions(identity)
trace_attack_path(identity, target)
get_recent_events(identity, 60s)
```

and mark the incident as:

- `contained`
- `partially_contained`
- `still_active`
- `verification_failed`

## 5. AI provider routing

The provider policy is fixed:

```text
             Incident analysis request
                       |
                       v
                Gemini API
                 /      \
             success    unavailable/error
               |                |
               v                v
          Gemini result   Local Gemma 4 12B
                              /      \
                          success   unavailable/error
                             |            |
                             v            v
                       AI result    deterministic
                                    availability fallback
```

### Primary provider: Gemini API

Gemini is the required headline cloud AI integration for the project.

### Fallback provider: local Gemma 4 12B

Use the instruction-tuned Gemma 4 12B model through a pre-running local inference server.

Recommended model identifier:

```text
google/gemma-4-12B-it
```

The local provider must implement the same analyzer interface and emit the same structured result schema as Gemini.

The router must switch to Gemma **only when Gemini is unavailable or fails**. It must not use both models simultaneously during normal operation.

Examples of Gemini failure conditions:

- missing API key;
- HTTP authentication failure;
- quota/rate limit error;
- timeout;
- transport/network failure;
- provider service error;
- invalid/failed model response after retry policy is exhausted.

The local model server must already be running. Do not load 12B weights during a request.

### Last-resort deterministic fallback

A deterministic result may be used only when both Gemini and local Gemma are unavailable.

It must be labeled clearly:

```text
AI Provider: Demo Fallback
```

Never label deterministic output as Gemini or Gemma analysis.

## 7. Attack-source architecture

The attacker is now external to MedShield.

Preferred architecture:

```text
               RED TEAM
                  |
          Stratus Red Team
                  |
                  v
       HomeoCare AWS Sandbox
                  |
             AWS telemetry
                  |
          +-------+-------+
          |               |
          v               v
      CloudTrail      CloudWatch
          |               |
          +-------+-------+
                  |
                  v
             EventBridge
                  |
                  v
            MedShield AI
                  |
            Defense tools
                  |
                  v
          HomeoCare AWS
```

Stratus Red Team's documented model is to execute granular cloud attack techniques against a live test environment, with explicit warm-up, detonation, revert, and cleanup phases. citeturn190631search10turn190631search13

This means the application must not fabricate attack activity to make the demo look active. It should detect activity that actually reaches the AWS sandbox.

## 8. Stratus integration requirements

Do not embed Stratus inside the MedShield request path.

The red-team runner is a separate operational component.

Recommended layout:

```text
infra/
  homeocare/
  medshield/
redteam/
  README.md
  scenarios/
  scripts/
```

The red-team runner should:

- authenticate only to the dedicated sandbox AWS account/role;
- execute only a defined scenario allow-list;
- expose a scenario status to the dashboard through a safe read-only integration if desired;
- record a correlation ID for each detonation;
- provide cleanup/revert instructions;
- never target resources outside HomeoCare.

Do not make the red-team component an unrestricted autonomous exploit framework.

## 10. Clinical-risk computation

Do not let the model freely assign clinical risk scores.

Use deterministic inputs from the digital twin.

Suggested scoring factors:

```text
clinical_risk_score = f(
    asset_criticality,
    reachable_clinical_services,
    path_depth_to_clinical_asset,
    disruption_cost,
    redundancy_available,
    active_access_level
)
```

The agent may explain the resulting score and use it in decision-making, but the raw score should be reproducible from the twin.

Example:

```text
Compromised identity
    |
    +--> EHR                criticality 10
    +--> Pharmacy           criticality 9
             |
             +--> Device Gateway  criticality 10
```

If the attack path reaches the simulated device gateway, the clinical risk should rise because the gateway is tagged as clinically sensitive. The product should not claim that an actual patient has been harmed or that an actual medical device has been controlled.

## 11. Response policy

The agent should optimize for:

```text
minimize cyber risk
while minimizing clinical disruption
```

For a candidate set of actions, evaluate:

- containment effectiveness;
- asset criticality;
- blast-radius reduction;
- operational disruption;
- reversibility;
- confidence in the underlying evidence.

Example decision table:

| Action | Cyber containment | Clinical disruption | Reversible | Preferred when |
|---|---:|---:|---|---|
| Disable compromised identity | High | Low | Yes | Identity is sufficiently identified |
| Isolate Pharmacy API | High | High | Yes | Service itself is actively compromised |
| Isolate device gateway | Very high locally | High | Yes | Gateway compromise is confirmed |
| Block source IP | Medium | Very low | Yes | Attack source is confidently identified |
| Shut down broad network zone | Very high | Critical | Maybe | Only as last-resort sandbox action |

Gemini can select and explain among these options, but tool-level policy must reject actions that violate HomeoCare safety constraints.

## 12. Human authorization model

The hackathon product may demonstrate autonomous defense inside the sandbox, but every action must be categorized as:

- `recommendation`
- `approved_simulation`
- `executed_sandbox_action`

For real production deployments, actions affecting hospital infrastructure would require organization-defined authorization and change-management controls.

The codebase must not imply that MedShield can autonomously operate a real hospital without human oversight.

## 14. AWS defensive action boundary

All real AWS actions must be implemented in dedicated Lambda/tool functions with explicit resource allow-lists.

Example pseudocode:

```python
def revoke_identity_access(identity_id: str) -> DefenseResult:
    identity = load_identity(identity_id)

    if identity.environment != "HomeoCare-Sandbox":
        raise PolicyDenied("Target is outside HomeoCare sandbox")

    if identity.is_protected_service_identity:
        raise PolicyDenied("Protected service identity")

    # Perform narrowly scoped sandbox action.
    ...
```

The policy layer must run before any SDK mutation call.

## 15. Event correlation and incident lifecycle

A single AWS event is not necessarily an incident.

Implement a correlation layer that groups related events by some combination of:

- identity;
- source IP;
- resource ARN;
- session ID where available;
- temporal proximity;
- action family;
- shared attack/technique correlation ID if the red-team harness provides one.

Incident states:

```text
new
  -> triaging
  -> investigating
  -> contained
  -> resolved
```

Exceptional states:

```text
investigating -> false_positive
investigating -> verification_failed
contained -> reopened
```

## 18. Demo scenario

The canonical two-minute demonstration should be:

### Phase 1: healthy HomeoCare

```text
8/8 monitored systems healthy
No active incidents
MedShield: ACTIVE
```

### Phase 2: red team begins

Stratus Red Team executes an authorized attack technique against the sandbox.

Do not show a fake local event sequence.

### Phase 3: telemetry arrives

Actual AWS event(s) reach EventBridge/MedShield.

### Phase 4: MedShield investigates

The agent identifies the actor/resource, maps it to a HomeoCare asset, and queries the dependency graph.

### Phase 5: clinical blast radius

The graph reveals:

```text
compromised identity
    -> pharmacy API
    -> medication workflow
    -> device gateway
```

### Phase 6: response options

MedShield compares multiple bounded response options.

### Phase 7: defense

MedShield executes the safest sandbox action.

### Phase 8: attacker loses access

The selected red-team activity is blocked or its relevant access path is removed. Do not claim that MedShield "stopped the entire attacker" unless the telemetry and verification actually support that conclusion.

### Phase 9: verification

Show the changed permission/path state and mark the incident contained.

## 19. Failure handling

If Gemini fails:

```text
Gemini unavailable
    -> route to local Gemma 4 12B
```

If local Gemma fails:

```text
Gemma unavailable
    -> deterministic availability fallback
```

If telemetry stops arriving:

```text
Telemetry stale
    -> MedShield status = DEGRADED
    -> do not falsely report containment
```

If a response action fails:

```text
Action failed
    -> status = verification_required
    -> do not mark incident contained
```

If an event cannot be mapped to a HomeoCare asset:

```text
Unknown resource
    -> classify as unmapped
    -> investigate resource identity
    -> do not invent clinical impact
```

## 20. Security and scope constraints

- Only authorized HomeoCare sandbox resources may be attacked or modified.
- Only allow-listed Stratus scenarios may be executed.
- Only constrained defensive tools may mutate AWS state.
- Never expose arbitrary command execution to the LLM.
- Never target production accounts.
- Never use real patient data.
- Never connect to real medical devices.
- Do not equate a simulated device-gateway compromise with confirmed patient harm.
- Treat AI output as decision support and evidence interpretation, not unquestionable truth.

## 21. Definition of done

The new MedShield architecture is complete when:

1. The old frontend simulation is gone from the primary workflow.
2. HomeoCare exists as an actual AWS sandbox environment plus a digital-twin dependency graph.
3. Stratus Red Team can execute at least one authorized AWS attack technique against the sandbox and provide a cleanup/revert path. citeturn190631search10
4. CloudTrail/CloudWatch telemetry reaches the MedShield event pipeline.
5. MedShield can map telemetry to HomeoCare assets.
6. MedShield can reconstruct an attack path.
7. MedShield can calculate deterministic clinical blast radius.
8. Gemini performs structured investigation/reasoning when available.
9. Local Gemma 4 12B is used only when Gemini is unavailable.
10. The deterministic fallback is used only when both AI providers are unavailable.
11. MedShield can select a bounded response action.
12. The response action is executed only inside the HomeoCare sandbox.
13. MedShield verifies the post-defense state.
14. The UI demonstrates the complete loop: **Attack -> Telemetry -> Investigate -> Clinical Impact -> Decide -> Defend -> Verify**.

## 22. What the coding agent must not do

Do not regress to the old architecture by:

- adding another fake `simulate attack` flow;
- generating hardcoded logs and presenting them as AWS events;
- making Gemini responsible for all graph/risk calculations;
- giving the model unrestricted AWS credentials or arbitrary command execution;
- putting Gemma 4 weights inside Lambda;
- building a generic chatbot instead of an event-driven security agent;
- claiming that the system is a production hospital cybersecurity platform;
- connecting the digital twin to real hospital infrastructure or physical medical devices.

The objective is not a flashy mock SOC. The objective is a **closed-loop, auditable, sandboxed healthcare cybersecurity defense system** in which an external adversary-emulation framework produces attack activity and MedShield demonstrates measurable defensive behavior against the HomeoCare digital twin.
